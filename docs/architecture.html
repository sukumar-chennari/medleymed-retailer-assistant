MedleyMed Retailer Assistant

System Architecture

A deterministic dispatch layer decides most turns without ever calling the model; whatever's left goes through a LangChain agent whose guardrail middleware intercepts every tool call before it runs and overrides the model's own reply after it responds.

control flow data read/write or merge guardrail middleware

Request lifecycle

  1. Message arrives at /api/chat.Text, or an image (routed to Gemini first — see below).
  2. Dispatch checks pending state first.Is there a clarifying question awaiting an answer, an address/email being collected, or a bare selection ("2", "last one") against a just-shown list? If so, resolve it in plain Python — the model is never called.
  3. No match → build the agent fresh.A new set of 6 tools and a new GuardrailMiddleware instance are constructed, closing over this turn's session_id, raw user text, and grounding state.
  4. ChatOllama decides whether to answer directly or call a tool.System prompt + full conversation history + the injected catalog hint (if the text names a symptom).
  5. wrap_tool_call intercepts before execution.A premature order, a hallucinated category switch, a misrouted info-question, or an incorrect decline can all be blocked, corrected, or redirected here — the underlying tool may never even run.
  6. Tool runs, result feeds back to the model.Loops up to ~6 rounds. lookup_medicine_info calls into the RAG subsystem; save_address/start_order write through store.py.
  7. after_agent overrides the final reply.Checks for a leaked tool name or an unverified completion claim (order placed / email sent / address saved) before the model's own wording ever reaches the user — replaced with a fixed template when needed.
  8. Response returns to the browser either way.Same ChatResponse shape whether it came from step 2 or step 7.
